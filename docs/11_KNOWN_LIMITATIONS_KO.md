## 0. 2026-11-04 실기: 원시 영상 QoS와 로봇 안 ROS 통신 정지

증거 수준: **실제 장치**(Pi 4B). 원인 판단은 **추정**이다.

- **증상**: 휴대폰은 연결·조종권을 잡았지만 수신기가 모든 활성 명령을 `not_owner (control_state 2.000s 넘게 미수신)`로 거부했다(안전 쪽 동작). 같은 때 웹 조종기의 로봇 상태가 갱신되지 않았고, 원시 영상(`/usb_cam/image_raw`) 전달이 0.55–2 Hz로 떨어졌다(압축 토픽은 14 Hz). usb_cam 메모리가 196 MB까지 늘었다(평소 66–88 MB).
- **같은 때 한 일**: web_video_server로 원시 영상을 기본 QoS(RELIABLE)로 받는 요청(스냅샷, `type=mjpeg`)을 보냈다. 서비스 재시작 직후 usb_cam이 종료 때 비정상 종료했다(exit −11).
- **확인한 것**: 서비스 멈춤 → `fastdds shm clean` → 시작으로는 잠깐만 회복했다. 전원을 껐다 켜자 회복했다. 다시 원시 영상을 기본 QoS로 요청하자 곧 같은 증상이 나왔다. 재부팅 뒤 `qos_profile=sensor_data`(best-effort)로 요청하자 mjpeg 8 s 3,874,322 B, 압축 8 s 8,772,423 B를 받았고 그 뒤에도 상태 나이 0.5 s 이하로 정상이었다.
- **판단(추정)**: 큰 원시 영상(장당 약 0.9 MB, 15 Hz)을 RELIABLE로 구독하는 쪽이 밀리면, 송신 쪽이 쌓아 두고 재전송하면서 로봇 안 ROS 통신 전체가 막힌다. 소프트웨어 재시작으로는 풀리지 않을 때가 있었고, 재부팅하면 풀렸다.
- **대응**: 원시 영상을 요청하는 모든 곳에 `qos_profile=sensor_data`(게이트웨이 기본값, 화면, Mac 조종기, 문서), `armpi.service` 시작 전 `fastdds shm clean`, 소프트웨어를 바꾼 뒤에는 서비스 재시작 대신 재부팅.
- **관찰(원인 미확정)**: `ROS_LOCALHOST_ONLY=1`로 띄웠을 때 `/dev/shm`에 8 MiB 공유 메모리 세그먼트가 보이지 않았다(역효과로 보고 쓰지 않음). ROS 명령줄 도구(`ros2 topic hz` 등)를 시간 제한(`timeout`)으로 끊은 직후에 증상이 나타난 적도 있다 — 로봇에서 진단할 때는 강제 종료하지 않는다. usb_cam(0.8)이 종료 때 세그폴트(exit −11)한다.
- **남은 것**: 실제 원인 미확정. RELIABLE 원시 영상 구독을 아예 막는 방법은 검토 전.

## 2. 하드웨어·제어 동작의 한계

1. **독립 하드웨어 비상정지가 없다.** 모든 정지 경로(UDP, 서비스, KEY1, watchdog)가 같은 Pi의 소프트웨어다. 커널 멈춤·전원 이상은 막지 못한다. 마지막 수단은 배터리 스위치다.
2. **제어 노드가 강제 종료될 때 바퀴가 멈추는지 모른다** [미확인].
   - 정상 종료 때는 바퀴 0을 쓰고 끝난다 [코드: `shutdown_outputs()`].
   - `kill -9`·크래시 때는 이 코드가 돌지 않는다. 모터 보드(I2C 0x34)가 마지막 속도를 계속 유지하는지 모른다.
   - 시험 E11에서 바퀴를 띄우고 먼저 확인해야 한다.
3. **제어기·수신기 노드는 자동 재시작되지 않는다** [코드: `armpi.launch.py`에서 `respawn`은 usb_cam·web_video_server에만 있음]. 노드 하나가 죽어도 launch는 계속 돌므로 systemd `Restart=on-failure`도 동작하지 않는다 [추정]. 이때 차체는 멈추지만(2차 watchdog 0.6 s) 다시 조종하려면 `sudo systemctl restart armpi.service`가 필요하다.
4. **서보 위치 피드백은 기본적으로 명령값이다.** `servo.read_position` 기본 false라 `/joint_states`·`/armpi/status`의 팔 현재값은 측정값이 아니다 [코드]. 상태에는 `position_source: "commanded"`로 표시한다. 화면에 "실제 팔 자세"로 보여 주면 안 된다.
5. **서보 단독 읽기 도구가 없다.** POS_READ·VIN_READ·TEMP_READ를 따로 불러 볼 실행 파일이 없다 [코드: 실행 파일은 `armpi_control_node`, `armpi_vr_bridge_node`뿐]. 서보 전압·온도는 어디에도 발행되지 않는다. 위치 읽기 실패 횟수도 토픽에 없다(로그로만 확인).
6. **RGB LED(BCM 12, WS2812 2개)는 새 노드에 구현되지 않았다** [코드: `ros2_ws/src` 검색 결과 LED·ws281x 코드 없음]. GPIO12(PWM)를 쓰려면 아날로그 오디오를 꺼야 한다(`dtparam=audio=off`).
7. **KEY2 종료는 별도 서비스에 달려 있다.** 제어기는 2 s 누름에 `/armpi/shutdown_requested`를 발행만 한다 [코드]. 22:32에 `deploy/systemd/armpi-shutdown.service`(토픽 1회 수신 → `systemctl poweroff`)가 추가되고 `ENABLED`에 올랐다 [코드]. 이 서비스는 root로 ROS 2 토픽을 구독하므로 DDS로 같은 토픽을 보내는 **같은 망의 누구나 로봇을 끌 수 있다**(`ROS_LOCALHOST_ONLY=0`) [코드·추정]. 실기·이미지 확인 전.
8. **KEY1은 비상정지 버튼이다.** 짧게 누르면 비상정지 latch(출처 `button`). `/armpi/reset_estop`으로만 풀린다 [코드].
9. **손목 회전(joint5)은 서보값 500으로 고정**이다 [코드: `arm.joint5_servo_value`]. 프로토콜 v3에도 손목 회전 필드가 없다. 디버그 입력(`/armpi/arm/joint_debug`)으로만 움직일 수 있다.
10. **실제 링크 길이에서는 손끝을 아래(pitch −90°)로 향하는 자세가 z ≈ 0 근처에서만 풀린다** [계산: `armpi_kinematics` 식, 손목→손끝 0.16331 m]. 예: `docs/01_PROTOCOL_V3_SPEC.md`의 예시 목표 `(0.15, 0, 0.12, −1.5708)`은 `ik_unreachable`이다 [계산]. pitch −45°~0° 쪽이 넓게 풀린다.
11. **보간 중 IK가 풀리지 않는 구간을 지나면 팔이 그 앞에서 멈춘다.** 수신기는 최종 목표만 검사하고, 제어기는 보간 중 IK 실패 시 직전 유효 자세를 유지한다(`arm_ik_blocked`) [코드]. 그리퍼만 계속 움직인다.
12. **차체 `armpi_arm_base` ↔ `base_link` 좌표 변환(TF)이 정해지지 않았다** [코드: TF 발행 코드 없음]. 팔 기준점이 차체 중심에서 어디에 있는지 모른다 [미확인].
13. **배터리 % 는 대략값이다.** 6.6–8.4 V 선형으로 계산한다. 실측 방전 곡선이 아니다 [코드].

## 4. 통신·보안

1. **인증·암호화가 없다.** UDP 5001/5002, rosbridge 9090, MJPEG 8080 모두 같은 망의 누구나 접근할 수 있다 [코드].
2. **rosbridge·DDS로 UDP 세션을 거치지 않고 로봇을 움직일 수 있다.** 제어기는 `/armpi/cmd_vel`·`/armpi/arm/target`을 누가 보냈는지 확인하지 않는다 [코드]. rosbridge(9090)로 이 토픽을 발행하거나 `/armpi/reset_estop`을 부를 수 있다. `armpi.service`는 `ROS_LOCALHOST_ONLY=0`, `ROS_DOMAIN_ID=0`이라 같은 망의 ROS 2 기기도 발행할 수 있다 [코드]. 이 경로에는 중립 확인·소유권 규칙이 없다(2차 watchdog 0.6 s와 stamp 0.5 s 검사만 있음).
3. **`allowed_sources`는 IPv4 출처 주소만 본다.** 주소는 위조할 수 있다. 기본은 빈 목록(모두 허용)이다 [코드].
4. **소유자가 아닌 클라이언트의 비상정지도 받는다**(`accept_estop_from_any_client: true`) [코드]. 안전 쪽 선택이지만, 악의적 클라이언트가 계속 latch를 걸 수 있다.
5. **Mac 조종기 화면은 127.0.0.1에서만 열린다** [코드: `ThreadingHTTPServer(("127.0.0.1", ...))`]. 다른 기기(휴대폰·Quest 브라우저)에서는 열 수 없다. 로봇 내장 웹 조종기(`armpi-web.service`)는 작성 시점에 없다.
6. **colima(Docker)는 UDP 포트를 Mac으로 넘기지 않는다**(2026-11-02 확인 기록) [코드: `tools/udp_tcp_relay.py` 설명]. 컨테이너 안 수신기를 Mac 조종기로 시험하려면 이 중계기를 써야 한다. 실제 로봇에는 필요 없다.
7. **대체 AP는 부팅할 때 한 번만 판단한다.** `armpi-net-fallback`은 oneshot이다. 부팅 뒤 60 s 안에 1순위 와이파이에 붙으면 끝난다. 나중에 1순위 와이파이가 끊겨도 AP로 바꾸지 않는다 [코드].
8. **대체 AP 비밀번호는 이미지를 만들 때 정한다.** 추측하기 쉬운 값을 쓰지 않는다(값은 문서에 적지 않음).

## 5. 시간·지연

1. **로봇에 RTC가 없다.** 시계는 `systemd-timesyncd`가 인터넷으로 맞춘다. 대체 AP(인터넷 없음)에서는 맞지 않는다 [추정].).
2. **프로토콜 v3에 송신 시각이 없다.** 늦게 도착했지만 번호가 증가한 패킷을 가려낼 수 없다 [코드: v2와 같음].
3. **두 기기 시계 차이로 한 방향 지연을 잴 수 없다.** 지금 쓸 수 있는 값은 조종기 쪽 왕복(RTT)뿐이다. RTT/2는 "두 방향이 같다"는 가정이 필요하다.
4. **지금 있는 지연 수치는 모두 루프백 값이다.**
   - 수신기 차체 watchdog 정지 0.403 s, 팔 유지 전환 0.407 s [시험 로그: (시험 기록), 컨테이너 루프백]
   - 가짜 로봇 ACK 왕복 중앙 2.62 ms, 최대 2.95 ms [시험 로그: (시험 기록), Mac 루프백]
   - 같은 시험의 "반영 55–163 ms"는 2 Hz 상태 토픽을 거친 값이라 제어 지연이 아니다.
5. **재시작하면 retire 목록이 사라진다.** `disconnect`한 UUID는 프로세스가 도는 동안만 거부된다(최대 1,024개) [코드].
